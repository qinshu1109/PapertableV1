# agent-bridge 文件桥协议

> 本文档成文于 2026-08-14，依据既有简报实践（briefs/ 至 19 号）归纳；此前协议并无成文总纲，散见各简报、GUARDRAILS.md 与 HANDOFF 文档（见 out/dsh-plugin-feasibility-2026-08-14.md「简报勘误一」）。本文记录**现状**而非设计新协议；与具体简报或 GUARDRAILS.md 冲突时，以后者为准。通用方法论版见 skills/agent-bridge-protocol/SKILL.md。

## 1. 这是什么

agent-bridge/ 是 Papertable 的多 agent 协作文件桥：kimi（herdr 里的主代理，通常任主控）、claude、codex、Cursor Agent 等异构 agent 围绕 papertableV1 仓库协作时，派单、产出、验收证据全部落成本目录下的普通文件。文件即档案：谁派的、依据什么、谁做的、验收凭什么，事后全部可查。

## 2. 目录职责

| 路径 | 职责 | 谁写 |
|---|---|---|
| `GUARDRAILS.md` | 守门红线：四类守门文件/动作任何 agent 不得自行修改＋提案语义＋沿用纪律；常驻，所有简报默认引用 | 用户拍板才改 |
| `briefs/NN-主题.md` | 派单简报，编号递增 | 派单方（主控） |
| `out/` | 执行产物：探索/评测报告、进度文件、修复说明 | 执行方 |
| `qa-evidence/` | 验收证据截图，命名 `NN-场景-状态.png`（NN＝对应简报号，实例：`15-mode-bar-recheck-hover.png`、`17-proposals-ops-after-reject.png`） | 验收方 |
| `HANDOFF-<任务号>.md` | 交接文档，换窗口接手用（实例：HANDOFF-PW-63.md） | 交出方 |

## 3. 简报：编号与结构

编号 NN 单调递增，一任务一号；复测简报沿用原编号加 R（标题「15R」，文件名 `15-mode-bar-frontend-recheck.md`），因此同一编号可有「验收＋复测」两份文件。

结构以 12/14/16/18/19 为实例归纳：

- **标题**：`NN · 主题`（12–17）或 `简报 NN：主题（任务性质）`（18/19 起的现行式样）；性质注明 开发（写代码）/ 探索（只读出报告）/ 验收（只验不改）。
- **红线引用句**：见 §4。
- **元数据块**（18/19 起）：发起方/主控、执行方、日期、性质或依据（上游报告路径）。12–17 无此块，直接进背景。
- **背景**：假设执行者零上下文（18 明写「你没有任何上下文，从这里读起」），给局面、动机、真值源文件路径。
- **规格**：做什么、怎么算对——表结构/状态机/接口用表格与代码块写死（12 的事件表、16 的状态机是范本），不让执行方猜。
- **红线/纪律/只读区**：本任务不许碰什么（12「红线（必须遵守）」、19「开工前必读（硬约束）」含可写区清单）。
- **验收（自行跑完再回报）**：测试全绿、真实 curl/运行输出贴原文；执行方自己跑完才有资格回报。
- **回报口径**：改动文件清单、测试命令与结果、输出摘录；探索/战役类任务指定产物文件名与进度文件（18/19）。
- **分工边界**：明确不归执行方的事及其归属（12「浏览器端验收由 codex 窗口负责」、16「前端与浏览器验收不归你」）。

## 4. 红线引用规矩

GUARDRAILS.md 于 2026-08-12 拍板生效，其中写死：每份派活简报开头必须写「先读 agent-bridge/GUARDRAILS.md，红线默认生效」。执行情况：14/15/15R/16/17 逐字照办；19 以「开工前必读」第 1 条展开（先读 GUARDRAILS＋四类守门零触碰＋疑似绕不开时停下请示）；12/13 早于该规矩生效，无此句；18 为纯只读探索，未写字面句，改以任务内「两仓只读」约束覆盖。今后新开的派活简报一律写字面句。

## 5. 执行方回报口径

- **会话内回报为主**：改动文件清单、测试命令与结果、真实输出摘录，直接回在执行会话里（12/14/16 的「回报」条目均如此）。
- **产物类报告才落 out/**，文件名由简报指定（18 指定 `dsh-plugin-feasibility-2026-08-14.md`；19 指定进度文件 `dsh-plugins-progress.md` 与总结 `dsh-plugins-final-2026-08-14.md`）。系列产物用「主题-标识-日期.md」（`voice-sieve-<bvid>-<日期>.md`，附录加 `-appendix` 后缀）；对某简报的修复说明用简报号前缀（`11-voice-matrix-single-run-fixture-fix.md`）。
- **不回写 briefs/**：简报是派单方单向输出；执行方异议写进回报或进度文件，不改简报原文。
- **长战役维护进度文件**：每个工作流一行状态（未开始/进行中/已完成/被卡＋一句话）＋环境事实＋守门红线状态＋阻塞/请示区（19 现行实例）；疑似绕不开红线时停下写请示区等主控，不自行其是。

## 6. 验收：独立简报＋证据

- 验收独立成单，验收人与执行人分离（13 验 12、15/15R 验 14、17 验 16）；验收人**只验收、不改代码**。
- 验收清单逐条给出入口路径、操作步骤、预期结果；关键项必须含一次**真实端到端动作**（13：做一次真实的人动作后账本对应计数 +1；17：人行使否决后状态真实落库）。
- **问题回路写明流向**：后端问题 → 写新简报（续编号）经 herdr 发 claude 窗口（w1:p9）修；前端问题 → 简报注明「前端问题，回 kimi」（前端只能 kimi 主代理亲自改，见 GUARDRAILS 沿用纪律）；修完复测，循环到全绿（15 → 15R 即一轮实例）。
- 证据落 `qa-evidence/NN-*.png`；回报＝逐条结论＋截图路径。

## 7. 投递通道与轮询

文件本身不产生通知，两端各自解决（通道实例见 HANDOFF-PW-63 §2）：

- **派单**：主控经 herdr 发一句 prompt 指到简报：

```bash
herdr agent list                 # 找目标窗口 TARGET
herdr agent prompt <TARGET> "读 agent-bridge/briefs/NN-主题.md，严格按它执行；完成后按简报末尾的回报口径汇报。"
herdr agent wait <TARGET> --timeout <ms>   # 等状态翻转（idle/done/blocked）再看
herdr agent read <TARGET> --lines 80       # 看输出；别轮询刷屏
```

- **收货**：主控**定时拉取**——读 out/ 报告与进度文件、读执行方窗格（18「写完后不用找我，我会定时来收报告」；19「你不主动找我，我走拉取通道」）。执行方完工不必主动找主控。

## 8. 交接文档 HANDOFF

任务中途换窗口/换 agent 时，交出方写 `HANDOFF-<任务号>.md`，**自包含**：新窗口一句「读 HANDOFF-XX.md，按它接手」即可上手，不用找上一个窗口。HANDOFF-PW-63 的六段结构：①你是谁、局面在哪（真值源清单）；②已拍板决定，别再问；③第一步做什么（带 herdr 命令）；④验收标准（不达标就打回）；⑤继承纪律（违反即返工——含「每个用户回合 MemOS 至少一读一写」等会话纪律的沿用口径，见其 §5）；⑥已做过的，别重复劳动。

## 9. 沿用纪律（汇总引用，细则以 GUARDRAILS.md §三与原简报为准）

- papertable 真库（`~/Library/Application Support/Papertable/papertable.sqlite3`）只读，绝不写。
- Memos 笔记库只读。
- 不 commit、不 push，除非用户明确要求。
- AI 摆证据、人下判断；AI 对正式表无写权限（铸币权在人）；「摆过 ≠ 用过」「自报通过 ≠ 验收通过」。
- 前端（frontend/ 一切实现、build、截图、验收）只能由 kimi 主代理亲自做，不派子代理/窗口。

# 简报 26 · 角度 B：微信侧通道调研

> 调研日期：2026-08-14（联网核验）  
> 范围：wechaty / gewechat / itchat 系 / 企业微信 / 公众号与客服消息 / 文件传输助手  
> 约束：只调研，不改代码。本文把“接口上能发消息”和“能否长期、合规、稳定地把定时任务结果推到手机”分开判断。

## 结论先行

如果今天就要做 MVP，推荐 **企业微信自建应用（WeCom API）**，接受入口从“个人微信私聊”变为“企业微信应用/企业微信会话”。它是唯一同时满足：官方接口、可主动推送、可接收用户消息、能发文本和文件、个人号封禁风险低、Mac 可部署 的现实路径。Mac 上的 dsh 可直接调用出站 API；入站消息需配置企业微信可访问的回调 URL，因此本机服务要有公网 HTTPS 入口或一个很薄的公网中转。

如果硬性要求是“个人微信号里随时和 agent 对话”，截至本次检索没有发现可承诺的官方常驻机器人 API。wechaty、itchat 系、gewechat 和“发文件传输助手”都依赖个人号的非官方登录/自动化，**技术上可以主动发，生产上不应承诺稳定，更不应拿重要个人号试错**。微信个人软件协议明确禁止未经腾讯授权的第三方软件登录、使用或自动化操作；因此封号/限制功能风险只能定性为高或不可控，不能用某个库的“能跑通”当作安全证明。

公众号/微信客服消息是合规的次选，但客服主动消息受用户最近一次互动后的时间窗和平台配额约束，不能等价于“每天任意时间把定时结果推给一个沉默用户”。文件传输助手不是机器人账号，也没有给本地程序使用的官方消息 API。

### 主动推送结论（按可用于 MVP 的强弱）

| 通道 | 定时任务主动推送 | 稳定性判断 | 个人号封禁风险 |
|---|---|---|---|
| 企业微信自建应用 | **可以，官方 API** | **强**；受应用可见范围、接口权限、频率/失败重试约束 | 低（不是个人号协议自动化）；仍有应用审核和运营规则 |
| 公众号/微信客服 | **有条件** | 中/弱；通常要求用户互动后 48 小时窗口，且有次数/资质限制 | 低（官方 API）；账号审核和内容规则风险仍在 |
| wechaty + 某个个人号 puppet | 技术上可以 | 弱；依赖登录态、puppet、设备/风控，不能给 SLA | 高/不可控 |
| itchat / itchat-uos / wxpy | 技术上可以 | 弱；项目老旧、会话易失，已有官方封禁警告 | 高 |
| gewechat | 历史上可以 | **当前不可作为方案**；项目已明确归档停维 | 高/不可控 |
| 文件传输助手 | 只能借助上述个人号自动化 | 弱；它不是 API 端点，且继承个人号自动化风险 | 高/不可控 |

## 通道逐项判断

### 1. wechaty（及 puppet 生态）

**维护状态。** Wechaty 本身是跨平台机器人框架，核心仓库和组织下的部分项目在 2025 年仍有更新；macOS、Linux、Windows 都是框架支持的平台。但 Wechaty 不是一个官方微信通道，实际能力和风险由 puppet 决定。常见的 `puppet-wechat` 是微信 Web provider，仓库文档仍列出 Web 登录限制：2017 年后注册的许多账号不能走 Web 登录，且存在建群/邀请等能力限制；其标准 Web 协议版本历史上长期没有跟进。商业/服务化 puppet 还需要 token，成本、可用性和账号策略由供应方决定。

**收发能力。** 框架层面可收发文本、图片、文件等消息，具体取决于 puppet；不能把某一 puppet 的能力当成所有 puppet 的保证。历史 Web puppet 也明确不支持企业微信 Work WeChat。

**主动推送。** 只要个人号已登录、连接未断，定时任务调用 `message.say/send` 在技术上能主动发送；但这依赖登录态、二维码/设备校验、puppet 服务和微信风控。断线重登、账号被限制、Web 协议失效都会让定时推送静默失败。因此适合一次性实验或隔离测试号，不适合作为 dsh 的唯一生产出口。

**macOS 与风险。** Node/Python 客户端可以在 macOS 运行；若走 Web 自动化/Puppeteer 或非官方 Pad/桌面协议，就是个人号自动化。微信协议把“插件、外挂、非经腾讯授权的第三方工具/服务接入”以及“非腾讯开发/授权软件登录、使用或自动化操作”列为禁止行为。故风险不是“wechaty 安全、某 puppet 不安全”的二元结论，而是：**个人号风险高且无可验证的封禁概率；框架维护不等于平台授权。**

**判断：** 有技术可行性，无生产稳定性或合规保证；不作为 MVP 首选。

### 2. gewechat

**维护状态。** 上游仓库 README 已明确写出“技术归档”“本项目已停止维护”，历史服务、Docker 镜像、部署和支持均不再提供，仓库只保留归档代码和文档。这比“更新慢”更强：不能假设今天还能获得可复现的服务端。

**收发与主动推送。** 历史版本曾提供 REST API（登录、联系人、群、消息、下载）以及 Webhook 异步事件，因此在旧环境里可以收消息、发文本/图片/文件，并由定时任务调用 REST 主动推送。但当前没有受支持的运行时、镜像或升级路径，故结论是“历史上能发，今天不能把它当可交付通道”。

**macOS 与风险。** 过去可通过 Docker/服务方式在 Mac 周边部署，但项目停止维护后，安装和故障恢复都没有可靠基线。它属于非官方个人号自动化；仓库也明确要求使用者自行承担风险、没有平台背书。封号、设备限制和数据合规风险均高/不可控。

**判断：** 直接排除，不投入 MVP 验证成本。

### 3. itchat 系（itchat、itchat-uos、wxpy 等）

**维护状态。** 原始 itchat 及其 Web 协议路线已经老化。`itchat-uos` 通过 UOS Web 微信绕过部分新号登录限制，但 PyPI 最新开发版本仍停留在 2022 年；项目 README 在 2023-02-10 明确记录“多数用户会收到官方封禁警告，暂时没有解决方案”，并提醒谨慎使用。wxpy/同类 fork 的 API 仍能找到，但不能据此推断平台兼容性或维护承诺。

**收发与主动推送。** 这些库通常能处理文本、图片、视频、附件/文件，也能把 `filehelper`（文件传输助手）作为收发对象。进程保持登录且会话存活时，定时任务调用发送函数在技术上可主动推送；`hotReload` 一类功能只是保存登录态，不等于断线/风控后的可靠恢复。实际故障模式包括二维码重新登录、Web 会话失效、消息漏收、发送失败和账号被限制。

**macOS 与风险。** Python 在 macOS 上运行没有门槛，但需要依赖旧 Web/UOS 路线或桌面自动化。项目明确出现官方封禁警告，配合微信协议对非授权自动化的禁止，故个号风险高；重要主号、支付号、工作号不应接入。

**判断：** 仅可用于一次性、隔离号、低价值实验；不适合常驻入口和定时任务生产推送。

### 4. 企业微信（WeCom）自建应用

**维护/合规状态。** 这是腾讯提供的正式企业应用通道，不需要模拟个人微信登录。自建应用可以配置“接收消息”回调：填写 URL、Token、EncodingAESKey，用户在应用中发消息后由企业微信推送到后台；官方文档要求回调服务器及时响应，并支持消息去重和超时后的异步主动回复。出站调用 `cgi-bin/message/send` 可按 `touser`、部门或标签发送应用消息，文档列出文本、图片、视频、文件、图文等消息类型。

**主动推送。** 定时任务可以直接用 access token 调用发送应用消息，不要求用户刚刚发过消息，因此是本报告唯一“无须个人号在线、适合定时结果”的强路径。仍要实现：应用可见范围校验、无效用户处理、限频/错误重试、重复消息保护和媒体上传过期管理。

**收发能力。** 入站以回调为主，支持文本和多种事件/媒体类型；出站至少覆盖文本、图片、视频、文件、图文。若需求是“一对一 agent 对话”，应将用户映射到企业微信 userid；如果需求是任意微信群，需另核对群聊能力和应用权限，不能把“应用消息”直接等价为普通个人微信群机器人。

**macOS 可行性。** dsh 完整运行在 Mac 没有问题，出站 API 由本机发起即可。入站回调 URL 必须能被企业微信访问；开发期可用安全的公网 HTTPS 隧道，生产期用小型公网 relay/reverse proxy 转给 Mac。不要把 Mac 局域网地址直接填进管理后台。

**风险。** 自动化发生在官方企业应用 API，不是个人号外挂登录，个人微信封号风险显著低得多；但仍受企业应用创建/审核、应用可见范围、接口权限、消息配额、内容和企业微信运营规则约束，不能宣称“零风险”。

**判断：** **推荐的 MVP 通道。** 代价是产品入口语义变成“企业微信应用”，不是个人微信私聊。

### 5. 公众号 / 微信客服消息

**维护/合规状态。** 公众号和微信客服走官方平台接口和回调，不需要破解个人号。用户关注、发消息、菜单点击等事件可推送给开发者；开发者可被动回复，或在客服窗口内用客服消息 API 异步发送。

**主动推送边界。** 客服消息不是无限制广播。公开开发文档长期规定：通常只有在用户互动后的约定时间窗（常见为 48 小时）内可发送，且受次数、账号类型、认证资质和平台规则影响。于是“用户刚和 agent 对话后，继续推送任务结果”可行；“用户几天不说话，定时任务仍任意推送”不能作为稳定承诺。公众号模板/订阅消息另有资格和模板约束，也不等同于个人聊天。

**收发、Mac 与风险。** 适合文本、图文/媒体等官方消息形态；具体消息类型要按账号类型和当前接口权限核对。Mac 端只是 HTTP API 客户端，入站同样需要公网可达回调。因走官方接口，个人号封禁风险低，但要承担账号审核、内容合规、接口配额和用户关系维护成本。

**判断：** 可做“用户主动发起后的客服式入口”或通知补充，不适合作为 dsh 常驻对话和无条件定时推送的唯一通道。

### 6. “发文件传输助手”类土办法

**先纠正对象。** 文件传输助手是微信内置的工具会话，不是一个给第三方程序调用的机器人账号。微信团队曾公开说明它是工具而非真实联系人；没有“向 filehelper 发 HTTP 请求”的官方 API。

**为什么看起来能用。** itchat 等个人号库可以把特殊用户名 `filehelper` 当作发送目标；桌面 UI/RPA 也能模拟点击。这些做法的底层仍是个人微信非官方自动化，所以文本、图片、文件虽然“能发”，但不获得任何额外合规性或稳定性。

**主动推送、macOS 与风险。** 定时推送必须依赖个人客户端在线、登录态有效和自动化层未被风控拦截；断线、升级、弹窗和账号限制都可能导致丢失。Mac 可以用桌面自动化或个人协议库实现，但风险继承 itchat/gewechat/wechaty 的最高档；同时文件传输助手会把内容同步到登录设备/云端链路，敏感文件不应通过此土办法转发。

**判断：** 不是独立通道；不要把它写成 MVP 方案或“低风险快捷入口”。

## 推荐落地（如果今天就要 MVP）

### 推荐路径：企业微信自建应用

1. 建一个最小自建应用，先只申请必要的消息和通讯录权限，把 dsh 使用者限定在应用可见范围。
2. 入站：配置回调 URL、Token、EncodingAESKey；公网 relay 只做签名校验、解密、转发和快速 200 响应，长任务在 Mac 本地执行。
3. 出站：定时任务完成后调用应用消息 API，优先文本/Markdown + 结果链接；需要下载时再上传临时媒体并发送文件。
4. 本地保留一个 outbox：消息 ID、目标 userid、发送状态、重试次数、最后错误；开启平台重复消息检查，避免定时任务重复推送。
5. 验收至少覆盖：用户消息入站、Mac 执行 dsh、回复文本、定时任务主动推送、断网重试、无权限用户、文件过期和撤回/失败告警。

### 如果产品方坚持个人微信

把个人号通道隔离成“实验适配器”，只用专门测试号验证交互，不把它作为生产通知唯一出口，不接支付/工作主号，不承诺不封号、不丢消息。真正需要可靠通知时，回退到企业微信应用或其他有官方 Bot API 的 IM；不要用文件传输助手掩盖通道本质。

### 证据边界

项目仓库的 star、最近提交和 README 只能说明公开维护/作者声明，不能证明微信平台会长期允许某种自动化。企业微信和公众号的“稳定”是接口层稳定，仍受账号资质、权限、配额、内容审查和平台变更影响。个人号的“高风险”是基于公开协议禁止条款、非官方登录方式和项目自身封禁警告作出的风险判断，不是对任何单个账号必然封禁的预测。

# 总判定

**你遇到的不是“内置助手能力不足”，而是“执行能力已经外置，协作台却仍按执行入口来定义自己”。**

更准确的重构方向不是给内置助手找一个降级岗位，而是把协作台改定义为：

> **外部智能系统的提案入口、证据审查面、权限边界、状态对账器和人类铸币层。**

协作台不必是 agent 的住所。成熟系统里的“协作”经常不是共处于一个聊天窗口，而是通过**工件、协议、状态迁移、验收和审计**发生。

而且，你原来的两条原则——“AI 提前摆好，人从看开始”“AI 摆证据、人下判断”——本来就和“以空白对话框为中心”有结构性冲突。外部 agent 没有制造这个冲突，只是把它暴露了。

自动化研究长期反复指出：自动化并不只是删掉人的工作，而会重组人的工作并产生新的协调、监控和接管问题；Bainbridge 的经典《Ironies of Automation》甚至明确指出，自动化可能扩大而不是消除操作员问题。([科学出版社](https://www.sciencedirect.com/science/article/pii/0005109883900468))

你这里最接近的组合解，不来自单一领域，而是：

**Pull Request/受保护分支的权威边界**
**＋ RPA Action Center 的待办交接**
**＋ GitOps 的状态对账**
**＋ 临床决策支持的独立审查**
**＋ 航空自动化的模式感知。**

# 1. 同构检索

## 判定

**没有一个领域完整经历并解决了你描述的全部问题，但多个领域分别解决了其中最关键的不同切面。**

真正值得借的不是“它们也有一个助手”，而是以下五个机制是否存在：

1. 执行引擎可以在工作台之外；
2. 工作台仍拥有权威状态；
3. 外部产出通过明确契约进入；
4. 正式状态迁移有人工或政策门；
5. 提议状态、正式状态和实际状态可以对账。

按这个标准，领域可以分成三类。

## A. 机制高度同构，可以直接借

| 领域 | 判定 | 真正解决的机制 | 与你的差异 |
| --- | --- | --- | --- |
| **Pull Request、CI、受保护分支** | **最强同构**，虽然历史起因不是“内置工具被架空” | 外部人、机器人和工具只能提出变更；自动检查提供证据；人批准后才进入权威分支；差异发生变化时，旧批准可自动失效；检查还能限定必须来自可信的特定系统。([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches?apiVersion=2022-11-28)) | 代码 diff 通常比“这个选题值不值得押”更容易机械比较。 |
| **RPA Action Center / Human-in-the-loop 工作流** | **强同构** | 自动化遇到异常、低置信度或需要业务判断时，创建人工任务；人在集中收件箱中批准、否决或补信息，自动化随后恢复。Blue Prism 还定义了 Pending、Locked、Complete、Exception、Deferred 等工作状态和优先级。([UiPath](https://www.uipath.com/blog/product-and-updates/uipath-apps-launch)) | RPA 任务通常比开放式 agent 产出更规则化；你的证据包必须更丰富。 |
| **临床决策支持与放射科 AI** | **强同构** | FDA 的“独立审查”模式要求使用者能够审查推荐依据，而不是主要依赖推荐；界面应提供用途、输入、算法和验证说明、相关已知与未知，并优先呈现决策相关信息、避免信息过载。ACR 的实践还包括本地验收、版本清单、漂移监控和停止规则。([U.S. Food and Drug Administration](https://www.fda.gov/media/191561/download)) | 医疗风险和监管强度远高于你的系统，但“AI 提供依据、人最终签署”几乎一一对应。 |
| **GitOps / Kubernetes 控制循环** | **强同构，主要解决状态问题** | 真正的模式不是“dashboard 变成只读”，而是期望状态声明化、版本化、不可变保存，由外部 controller 持续观察实际状态并对账；controller 还要把观察到的状态报告回来。([OpenGitOps](https://opengitops.dev/)) | 基础设施通常存在较明确的期望状态；战略内容判断不存在唯一可计算的 desired state。 |
| **算法交易、OMS/EMS 与外部算法** | **强同构，主要解决控制权问题** | Bloomberg EMSX API 允许 Excel、Python、Java 等外部程序管理和自动化交易；但监管层要求预设限额、错误订单阻断、授权访问、即时成交报告、实时可调整的风险控制及按时间排序的记录。执行可以外置，风险门不能外包。([EMSX API 文档](https://emsx-api-doc.readthedocs.io/en/latest/introduction.html)) | 交易中很多动作无法等到事后人工批准，因此重点是预执行硬门；你的大部分内容判断可以采用事前人工验收。 |
| **MES、SCADA、工业报警管理** | **强同构，主要解决层级和例外管理** | ISA-95 明确区分物理过程、控制、制造运营和业务规划层；MES 并不只是看板，而是管理运营。ISA-18 则把报警哲学、优先级、合理化、生命周期和 HMI 情境感知当作完整系统来治理。([isa.org](https://www.isa.org/standards-and-publications/isa-standards/isa-95-standard)) | 工业系统中的“异常”通常可测量；“哪个选题更值得做”不是异常检测问题。 |
| **SRE / 运维监控** | **强同构，适用于你的 agent 运行健康，而非内容判断** | Google SRE 把监控输出分为立即需要人处理的 page、数日内处理的 ticket，以及只用于以后分析的 logging；所有打扰人的 paging 都应可行动，否则会造成疲劳并掩盖真正问题。([Google SRE](https://sre.google/sre-book/being-on-call/)) | 它适合监控 agent 失败、同步延迟、权限异常和检查失败，不适合决定内容方向。 |

### 你漏掉的两个最重要领域

一是 **PR/CI/受保护分支**。它和你的“外部 agent 产出、自动验收、人铸币”结构最接近。

二是 **临床决策支持**。它对“什么才算给人提供了真正可独立判断的证据”有比一般 AI 产品成熟得多的回答。

## B. 只在部分结构上同构

### 呼叫中心：模式分离是同构的，工作台定位只部分同构

呼叫中心已经把两种东西分开：

- Agent Assist：人正在处理会话，AI 给知识、回复或摘要建议；
- autonomous self-service：AI 自主多步执行，遇到条件时通过明确的 Escalate 或 return-to-control 动作把控制权交还给人，并附带原因、摘要、意图等上下文。([AWS 文档](https://docs.aws.amazon.com/connect/latest/adminguide/agentic-self-service.html))

真正的教训不是“把 copilot 做强”，而是：

> **不要让 copilot 模式、自治模式和人工接管模式在界面上模糊地混在一起。**

另外，一项覆盖五千多名客服人员的研究发现，生成式 AI 助手的平均生产率增益主要集中在经验较少的人员，最高技能或最有经验者几乎没有明显正效应。对一个高度熟悉自己系统的单人专家而言，通用解释型 copilot 使用率低并不反常。([斯坦福人工智能研究所](https://hai.stanford.edu/news/will-generative-ai-make-you-more-productive-work-yes-only-if-youre-not-already-great-your-job))

### IDE：真正同构的是 LSP/DAP，不是内置终端

IDE 的成熟解法并不是不断把所有语言服务、调试器和工具链重新实现一遍，而是使用 LSP、DAP 等稳定协议，让语言智能和调试引擎成为可替换的外部组件，IDE 负责上下文、导航和交互呈现。([微软 GitHub](https://microsoft.github.io/language-server-protocol/))

这对你的启示很强：

> 不要集成某一个 agent 产品；定义一个所有 agent 都能提交的稳定“提案协议”。

但 IDE 不太解决人工审批、证据和正式状态问题，因此只能借“宿主—外部引擎”这一半。

### DAW 与插件：宿主模式同构，审查模式不同构

VST 把处理器和编辑控制器分开；宿主提供输入输出流、参数、自动化和会话环境，插件可以被宿主当作具有输入、输出和参数的黑盒。([Steinberg Media](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/API%2BDocumentation/Index.html))

它支持“工作台负责路由、状态和会话，能力由外部组件提供”的判断。

但 agent 不能完全当黑盒：你的正式判断需要来源、证据、版本、检查和责任轨迹。DAW 的黑盒容忍度不能照搬。

## C. 警示同构，不是成功解法

### 航空驾驶舱

航空是重要参照，但不是“自动驾驶接管后，飞行员成功转为监控员”的成功故事。

FAA 至今仍专门规定自动化环境下的 pilot monitoring 职责；航空人因资料持续把 mode transition、mode reversion、mode confusion 和 automation surprise 当作核心问题。([联邦航空管理局](https://www.faa.gov/regulations_policies/advisory_circulars/index.cfm/go/document.information/documentid/1030486))

它给你的警告是：

- 人不能只在极少数失败时突然接管；
- 当前模式和权限必须显式；
- 被动看大屏不等于保持情境感知；
- “最后还有一个人工按钮”并不等于人仍然具有实质控制。

因此，**砍掉对话、改成纯展示**不能以航空为正面依据。航空恰好说明纯监控会制造新的风险。

# 2. 工作台变成“监督和验收外部系统”后，界面应当长什么样

## 判定

**它不应成为一个普通 dashboard，也不应成为另一个 agent 操作台。它应是“双通道控制与验收界面”：**

1. **规范性决策通道**：凡是必须由你判断的事项，全部进入待验收队列；
2. **运行例外通道**：只有机器可判定、且确实需要你行动的异常才打扰你。

这两个通道不能混为一谈。

“这个 agent 的测试失败了”适合 management by exception。

“这五个选题中押哪一个”不是 exception；每一个都属于正常的人类判断工作，应进入 decision inbox。

## 一个较稳定的界面骨架

```text
┌──────────────── 模式与权限条 ────────────────┐
│ 当前执行者 / 当前写权限 / 基准版本 / 同步状态 │
│ 下一行动者 / 最后一次状态变化 / 是否可暂停    │
└───────────────────────────────────────────────┘

┌──── 待我判断 ────┬──── 运行异常 ────┬── 进行中/已结账 ──┐
│ 12 个提案         │ 2 个需行动事件    │ 状态与结果          │
└───────────────────────────────────────────────────────┘

选中提案后：

[要求我决定什么]
[相对基准改了什么]
[支持证据] [反证/缺失] [自动检查]
[产出者、任务简报、工具/版本、时间线]
[正式状态 / 实际状态 / 是否已过期]

[接受] [退修] [否决] [暂缓] [在原生工具中打开]
                     [询问此提案]

```

**空白对话框不再是首屏。**
聊天若保留，应成为“询问当前提案”的附属抽屉，而不是一个自称了解全部系统的全局主体。

## 六个机制的前提和失败模式

| 机制 | 前提条件 | 典型失败模式 |
| --- | --- | --- |
| **Management by exception** | 正常状态可观测；阈值和响应动作明确；检测质量足够；人有能力处理 | 报警洪水、低价值提醒、假阳性、静默漏报、所有事情都被标成“异常”。ISA-18 和 SRE 都把报警合理化、优先级和可行动性作为核心，而不是简单增加通知。([isa.org](https://www.isa.org/standards-and-publications/isa-standards/isa-18-series-of-standards)) |
| **待验收收件箱** | 每项是固定、可独立审查的单元；有请求动作、负责人、优先级、年龄和基准版本 | 垃圾抽屉、审批积压、低优先级永久饿死、一次提交过大、移动靶审批、人工机械盖章。Blue Prism 明确警告优先级可能让低优先级项永不被处理。([蓝图机器人文档](https://documentation.blueprism.com/bp-7-5/en-us/helpQueues.htm)) |
| **审计轨迹** | 稳定 ID；明确区分提议者、批准者和执行者；记录版本、差异、证据、时间和下游效果 | 把对话转录当审计；文件被覆盖；无法知道批准的是哪个版本；agent 自称“测试通过”却无可信检查来源。交易监管要求按时间排序的记录，受保护分支则把批准绑定到具体 diff。([欧洲证券和市场管理局](https://www.esma.europa.eu/publications-and-data/interactive-single-rulebook/mifid-ii/article-17-algorithmic-trading)) |
| **状态对账** | 有且只有一个正式事实源；外部观察带版本；导入幂等；能区分提议、正式、实际 | 双写、split brain、旧检查挂在新版本上、审批后基准变化、状态闪烁。Argo CD 建议利用 observedGeneration，正是为了避免 controller 尚未完成对账时错误翻转健康状态。([Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/health/)) |
| **模式感知** | 模式有限且命名明确；显示谁正在做、谁有权写、下一棒是谁、自动化是否暂停 | 你以为 agent 已停止但它仍在运行；你以为结果只是草稿但下游已消费；静默切换权限；自动化 surprise。航空经验说明“谁在开车”必须持续可见。([联邦航空管理局](https://www.faa.gov/regulations_policies/advisory_circulars/index.cfm/go/document.information/documentid/1030486)) |
| **人工验收门** | 有足够时间；能看到独立依据；动作范围明确、最好可回滚；不存在诱导性默认批准 | 人只做礼仪性点击；推荐、证据和解释全来自同一个故障源；信息过载；紧迫情况下发生 automation bias。FDA 特别把独立审查能力、时间压力和自动化偏误联系起来。([U.S. Food and Drug Administration](https://www.fda.gov/media/191561/download)) |

另一个容易忽略的原则是：

> **收件箱不是事实库。**

Blue Prism 的文档明确说 work queue 不应被当作永久的事实记录。对你来说，验收队列应该是一个由提案账本计算出的投影，而不是系统的权威状态本身。([蓝图机器人文档](https://documentation.blueprism.com/workhq/en-us/digital-workers/operations/work-queues.htm))

# 3. 三条候选补丁分别属于什么，致命假设是什么

## 判定

**你的三条候选都主要在改“表面交互”，没有改外部产出如何进入、谁拥有正式状态、如何验收和对账。因此它们确实更像补丁。**

| 候选 | 所属机制 | 致命假设 | 可以保留的窄用途 |
| --- | --- | --- | --- |
| **把内置助手做深** | 重新内化执行能力、垂直整合 | 假设协作台的价值取决于它是否拥有最强 agent；假设内外两个执行平面不会形成工具、权限、上下文和审计的双重体系 | 极低延迟的局部微操作、离线或隐私场景、只在当前工件中做小范围查询 |
| **降级成解说员** | 可观测性或叙事层 | 假设缺的是自然语言解释；假设“同一个模型替自己的结论讲理由”就增加了可审查性 | 针对已选中提案，基于明确来源回答“这个数字来自哪、这个 diff 为什么出现” |
| **砍掉对话，改成纯展示** | 被动 wallboard | 假设“看见状态”就等于“拥有监督”；假设用户可以长期靠警觉性发现真正问题 | 作为第二屏、远观大屏、历史趋势面板 |
| **第四条：控制与验收平面** | 提案裁决、权限门、状态对账、审计 | 不要求工作台拥有 AI，只要求它拥有权威边界 | 作为协作台的新主职能；聊天只是一种可选检查工具 |

第一条还有一个更严重的问题：它会制造**两个行动源**。同一件事可以由终端 agent 做，也可以由内置 agent 做，随后你必须回答：

- 哪个结果更权威？
- 两边是否用了相同数据快照？
- 两边的权限是否相同？
- 其中一边修改后，另一边的上下文何时失效？
- 失败和责任轨迹记在哪里？

第二条可能有价值，但必须从“全局解说员”缩成“工件级检查器”。否则它只是把缺乏结构化证据的问题包装成更流畅的文字。

第三条只有在已经存在可靠的提案契约、异常系统、状态迁移和审计时才成立。没有这些，纯展示只是“看起来很稳的静态墙”。

## 第四条的本质

可以把它叫作：

- **提案裁决台**
- **控制与验收平面**
- **人类铸币层**
- **外部 agent 的入境口岸**

它不负责成为最聪明的 agent，而负责将任何人、脚本或 agent 的产出统一变成：

> 固定版本的提案
> ＋ 可独立审查的证据包
> ＋ 自动检查
> ＋ 明确权限
> ＋ 人类状态迁移
> ＋ 可追溯的正式应用。

# 4. “助手是摆设”的度量是否用错了

## 判定

**在“这个助手是不是一个成功功能”的层面，你的判断是对的；在“协作台是不是健康”的层面，使用频率是错尺子。**

如果助手的工作就是让你经常和它聊，那么低使用率说明它没有找到需求。

但如果协作台的新工作是减少无价值干预、提高判断质量、保护权威状态，那么健康状态甚至可能是：

- 很少打开聊天；
- 很少收到运行异常；
- 只有少量高价值事项等待判断；
- 正常流程在外部工具中安静完成；
- 你花较短时间完成高质量验收。

SRE 的目标就是只让真正需要行动的事件打扰人；RPA 的目标也是让常规路径 touchless，只在例外或判断点创建人工任务。对高技能用户，通用 copilot 的边际价值本来也可能很低。([Google SRE](https://sre.google/sre-book/service-best-practices/))

## 更合适的健康指标

| 维度 | 建议指标 | 它回答的问题 |
| --- | --- | --- |
| **使命结果** | 任务简报到正式决定的周期；选题到发布周期；发布到转化/销售结账周期；每次押注的销售或转化结果 | 系统是否服务了“做内容为了销售” |
| **吞吐** | 每周进入、验收、退修、否决和结账的提案数；队列年龄中位数和 P95 | 产出是否真的通过了系统，而非堆在外面 |
| **质量与稳定性** | 一次验收通过率；退修率；正式后重开/回滚率；漏过问题率；结账后判断反转率 | 快是否以返工和错误为代价 |
| **人类注意力** | 每个最终接受项所需审查分钟数；每天被打断次数；无行动提醒占比；上下文切换次数 | 协作台是在节省判断力还是消耗判断力 |
| **状态完整性** | 外部状态同步延迟；旧基准审批数；重复/冲突提案数；对账失败数；状态误报和闪烁次数 | 界面展示的是否真是当前状态 |
| **证据质量** | 来源覆盖率；可复现检查覆盖率；反证/未知项覆盖率；证据过期率；agent 自报检查与可信检查的差异 | 你是否真的能独立判断 |
| **权限与审计** | 非人类正式写入成功数；越权尝试数；绕过审批数；无来源正式记录数；每次正式变化的签名覆盖率 | “铸币权在人”是否是技术事实 |
| **人因健康** | 模式误解次数；接受后立即重开的比例；异常短的审批时间；长期接近 100% 的无异议接受率 | 人是否已经变成橡皮图章 |

DORA 的成熟经验也是把系统表现拆成吞吐和不稳定性，而不是统计 dashboard 点击量；Google SRE 在衡量自动化时建议关注延迟、错误率、返工率和节省的人类时间。([Dora](https://dora.dev/guides/dora-metrics/))

ACR 的做法还提醒了一点：一次通过验收不是终点，还要持续监控实际表现、漂移和不一致案例。映射到你的系统，就是**定稿后仍要有发布、转化、结账和反事实回流**。([美国放射学会](https://www.acr.org/News-and-Publications/Media-Center/2026/first-practice-parameter-for-imaging-ai))

因此，“助手没被使用”可以是健康信号，但必须同时满足：

1. 外部自动化的结果质量确实好；
2. 失败和漂移能被发现；
3. 正式状态没有被绕过；
4. 你不是因为界面不可信而干脆不用它。

# 5. 外部 agent 的产出应如何进入，才不算越权

## 判定

**外部 agent 自动写入 pending\_review 完全可以合规，但前提是它写入的是“非权威提案”，而不是仅仅把正式记录的状态字段写成了 pending。**

权威性不由“是否落 SQLite”决定，而由以下问题决定：

- 下游是否把它当作正式事实；
- 它能否触发发布、结账或正式分析；
- 谁能把它转成 accepted/final/published/settled；
- 它是否绑定了固定基准版本；
- 是否可以覆盖或删除既有决策轨迹。

## 最清楚的三主体分工

自动化类型研究通常区分信息获取、信息分析、决策选择和动作实施。你的铁律可以被更精确地写成：([IEEE Xplore](https://ieeexplore.ieee.org/document/844354))

| 主体 | 权限 |
| --- | --- |
| **提议者：外部 agent** | 读正式状态；生成候选、草稿、diff、证据和检查请求；提交或撤回自己的提案 |
| **批准者：你** | 选择、退修、否决、接受；授权特定版本进入正式状态 |
| **实施者：可信系统服务** | 在收到“人类批准＋具体提案版本＋基准版本仍匹配”后，机械执行正式写入 |

这意味着：

> “铸币权在人”不等于每个正式字节必须由人手工输入。
> 人批准一个具体且版本锁定的变更后，由可信服务自动应用，仍然是人类授权的动作实施。

## 一个最小提案包应包含什么

```text
schema_version
proposal_id
target_object_id
target_base_version / base_hash
task_brief_id

proposed_by
agent_product / model_or_runtime_version
tool_or_skill_versions
scope_and_permissions

proposed_delta / draft / patch
artifact_refs
evidence_for
evidence_against
known_unknowns

checks:
  check_name
  check_source
  checked_version
  result
  artifact_ref

risk_and_impact
requested_human_action
created_at
expires_at
status

```

状态可以类似：

```text
draft
→ submitted
→ in_review
→ changes_requested | rejected | accepted
→ applied
→ verified
→ settled | rolled_back | expired

```

外部 agent 可以进入 submitted。

只有人可以进入 accepted、rejected、finalized、published 或 settled。

自动检查可以把自己的 check 标成通过，但不能把提案本身标成接受。

## 协作台应该摆什么

### 对每项产出必须摆

- **你被要求决定什么**
- 相对哪个基准版本发生了什么变化
- 支持证据、反证、缺失信息和不确定性
- 数据来源、快照时间和证据新鲜度
- 自动检查结果及其可信来源
- 任务简报、产出者、工具和版本
- 影响范围、可逆性和回滚方法
- 当前谁拥有下一步行动
- 提议状态、正式状态和实际状态是否一致

FDA 的独立审查原则很适合直接移植：展示用途、输入、依据、验证和相关已知/未知，并把最决策相关的信息前置，而不是让用户淹没在细节中。([U.S. Food and Drug Administration](https://www.fda.gov/media/191561/download))

### 默认不该摆

- 原始 chain-of-thought；
- 几百条工具调用流水；
- 完整终端转录；
- 没有校准依据的“置信度 97%”；
- 每个 agent 的中间工作噪声；
- 把 agent 自己生成的解释当成独立证据；
- 尚未冻结版本、仍在继续变化的“待批准结果”；
- 用一个绿色总分掩盖反证和失败检查。

这些内容可以作为诊断材料下钻查看，但不应成为业务判断证据的主视图。

## 不同产出的正确进入形式

### 代码

代码仍留在 Git 分支、commit、PR 和 CI 的原生环境中。

协作台只保存：

- 分支/commit/PR 标识；
- 任务简报；
- 变更范围和业务影响；
- 自动测试及可信检查来源；
- 浏览器验收报告；
- 回滚信息；
- 你的接受或退修记录。

不要在内容生产协作台里重做一个低配 IDE。

### 验收报告

以不可变工件或内容哈希进入，外加结构化摘要：

- 环境；
- 被测版本；
- 验收项；
- 通过/失败；
- 截图或录像工件；
- 未覆盖范围；
- 生成者与时间。

### 内容草稿

以绑定 target\_base\_version 的 revision 进入；一旦提交审查，该 revision 冻结。agent 继续修改时必须产生新 revision，旧批准自动失效。这正是受保护分支“diff 变了就重审”的逻辑。([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches?apiVersion=2022-11-28))

## 一个你没有明确提到、但非常危险的越权路径

你的外部 agent 不只是调用业务 API，还能修改系统代码。

因此最危险的越权不一定是：

> agent 直接把某条记录改成 final

而可能是：

> agent 修改了“只有人才能 final”的授权代码、数据库迁移或部署逻辑。

如果 agent 能改守门人，那么铁律只是文档，不是控制。

所以人类审批边界还必须覆盖：

- 权限和状态机代码；
- 数据库迁移；
- 正式环境部署；
- 用于验收的可信检查定义；
- agent 的运行凭据和可写路径。

受保护分支的 no-bypass、可信检查来源，以及交易系统要求风险控制保持在责任主体的直接、排他控制下，都是同一个机制。([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches?apiVersion=2022-11-28))

在本地 SQLite 系统里，如果外部 agent 拥有直接文件写权限，仅靠一列 status 很难形成真正边界。比逻辑约定更强的做法是让 agent 只能写 proposal API、独立 staging 数据库或受限目录，而正式数据库只能由可信应用服务写入。

# 6. 与现有系统结构怎么咬合，什么最不容易再次失效

## 判定

**第一落点应是数据流和权限语义；第二落点才是交互；第三是屏幕分工。**

最不耐久的是：

- 换更强模型；
- 给内置助手继续加工具；
- 把聊天框换成另一种聊天框；
- 为某一个外部 agent 写深度定制接口。

最耐久的是：

> **统一提案契约**
> **＋ 人类状态迁移**
> **＋ 权威数据服务**
> **＋ 对账和审计。**

因为无论未来的生产者是 Codex、Claude、另一个 agent、脚本还是人，它们都只是“提案生产者”。

## 建议的数据流形态

```text
外部 agent / 人 / 脚本 / CI
          │
          │  proposal manifest / local API / watched folder
          ▼
┌─────────────────────────────┐
│ 提案入口                    │
│ schema 校验                 │
│ 身份与权限校验              │
│ 基准版本校验                │
│ 幂等与重复检测              │
└──────────────┬──────────────┘
               ▼
┌─────────────────────────────┐
│ 提案账本 + 决策事件账本      │
│ append-only history         │
└───────┬────────┬────────────┘
        │        │
        │        └── agent 运行与异常视图
        └─────────── 待验收队列 / 内容卡片投影
               │
               ▼
       人类接受 / 退修 / 否决
               │
               ▼
┌─────────────────────────────┐
│ 可信正式写入服务             │
│ 再验证 base version         │
│ 应用精确变更                │
│ 记录 applied receipt        │
└──────────────┬──────────────┘
               ▼
       正式 SQLite 数据
               │
               ▼
       验证 / 发布 / 转化 / 结账
               │
               └──── 回流到后续证据与度量

```

传输方式可以先很朴素：

- 一个受监控的本地 inbox/ 目录；
- 一条 CLI 提交命令；
- 一个本地 HTTP API；
- 一个 staging SQLite 文件。

真正需要稳定的是 envelope 和状态语义，而不是传输技术。

这相当于把 LSP/DAP 的“外部能力、稳定协议”思想，与 GitOps 的“版本、对账”以及 PR 的“提议、检查、批准”组合起来。([微软 GitHub](https://microsoft.github.io/language-server-protocol/))

## 屏幕职责应如何重新划分

你的系统实际上出现了两条生产线：

1. **内容生产线**：选题、素材、成品、转化、结账；
2. **系统维护线**：代码、测试、浏览器验收、部署、修复。

它们可以共享提案协议、身份、审计和状态机，但不应该共享一个无差别的大收件箱。

### 内容决策屏

负责：

- 候选和草稿；
- 数据证据；
- 销售假设；
- 业务判断；
- 定稿和结账；
- 历史相似押注及结果。

### Agent 运行与系统维护屏

负责：

- 当前有哪些 agent run；
- 任务简报和产出工件；
- 代码/CI/浏览器验收状态；
- 阻塞、失败、重试、暂停；
- 权限和同步异常；
- 谁拥有下一步。

### 原生工具

继续负责其擅长的深度操作：

- 代码看 Git/IDE；
- agent 过程看终端；
- 页面验收看浏览器和报告；
- 协作台只持有入口、状态、证据索引和验收结果。

ISA-95 的一个耐久思想正是按活动责任划边界，而不是按当下技术产品划边界。([isa.org](https://www.isa.org/standards-and-publications/isa-standards/isa-95-standard))

## 三种状态必须分开显示

| 状态 | 你的系统中的含义 |
| --- | --- |
| **Proposed** | agent 建议变成什么 |
| **Official** | 你已经批准、系统正式记录为什么 |
| **Actual** | 外部世界或运行系统现在实际上是什么 |

例如：

- Proposed：建议发布版本 B；
- Official：你批准发布版本 B；
- Actual：平台上仍是版本 A，或发布失败。

又如：

- Proposed：agent 报告测试通过；
- Official：你批准这一变更；
- Actual：当前运行环境的 commit 和接受时并不一致。

只显示一个“已完成”会把三者全部压扁，是最常见的状态错觉。

# 你描述里最值得纠正的错误假设和漏坑

1. **“协作台必须有一个 AI 助手才算协作台。”**
错。协作可以是工件和状态迁移驱动的，聊天只是一种交互方式。
2. **“外部 agent 与内置助手是同一个岗位的竞争者。”**
只有在你坚持让协作台拥有执行平面时才是。把协作台改成控制与验收平面后，外部 agent 是生产者，协作台是边界。
3. **“从看开始”与“全局聊天为核心”可以同时成立。**
实际上两者冲突。你的原始使命已经预示首屏应是队列和证据卡，而不是空白输入框。
4. **“只读界面就是安全界面。”**
错。过期、模糊、无版本的只读状态同样危险；航空和 GitOps 都说明错误状态感知会制造 automation surprise 和状态闪烁。
5. **“pending\_review 是一个安全边界。”**
错。它只是字符串。真正边界是下游语义、API 权限、状态迁移规则、基准版本和部署控制。
6. **“人最后点了一次按钮，就算人下判断。”**
错。没有时间、独立依据、反证和干预能力时，最后一击只是礼仪性审批。
7. **“解释就是证据。”**
错。同一模型为自己的结果生成一段理由，可能只是把同一故障源变得更有说服力。
8. **“队列可以顺便当事实库。”**
错。队列是工作投影；事实应在独立、可审计的账本中。
9. **“把所有外部 agent 结果都塞进同一大屏会更统一。”**
未必。代码验收、内容押注和销售结账的证据结构完全不同。应共享协议和身份，但使用不同审查模板。
10. **“外部 agent 没有正式数据写权限，所以权限铁律已经成立。”**
不充分。agent 如果能改代码、迁移、部署和守门逻辑，就能间接改变正式写入规则。
11. **“agent 越强，人需要看的东西越少。”**
只对运行细节成立。agent 产出越多，越可能形成 review debt；审查单元、优先级、证据浓缩和队列容量反而更重要。
12. **“内置助手没人用就是系统浪费。”**
更准确的说法是：现有对话功能没有工作。已经投入的读数据和起草能力仍可被缩成工件级检查器，但没有必要为了回收沉没成本继续把它放在舞台中央。

# 如果只能改一处：候选清单

以下不排序，只列它们分别买到什么、牺牲什么。

| 只改这一处 | 直接获得的能力 | 跨领域依据 | 代价与未解决问题 |
| --- | --- | --- | --- |
| **增加“提案包＋状态机＋决策事件账本”** | 把人类铸币权从原则变成数据结构；外部 agent 可替换；批准绑定具体版本 | PR/受保护分支、GitOps、交易风险控制 | 后端和迁移工作最大；短期界面观感可能几乎不变 |
| **把首屏聊天换成待验收收件箱** | 立即符合“从看开始”；让真实外部产出进入日常动作 | UiPath Action Center、Blue Prism work queue | 没有规范的提案包时会迅速变成垃圾抽屉和橡皮图章流水线 |
| **给每张卡增加独立审查证据包** | 最直接落实“AI 摆证据、人下判断”；提高判断质量 | FDA CDS 独立审查、放射科 AI 验收和漂移监控 | 不能单独解决状态同步、权限绕过或队列积压 |
| **增加全局模式与对账条** | 明确谁在做、谁能写、下一棒是谁、状态对应哪个版本；减少 split brain | 航空模式感知、Kubernetes/Argo reconciliation | 不解决外部产出如何进入，也不提升单项证据质量 |
| **把内容决策屏与 agent 运维/系统维护屏拆开** | 避免代码验收噪声污染内容判断；责任边界更稳定 | ISA-95 分层、IDE 宿主模式 | 增加界面数量和跨屏跳转；仍需要共享数据契约 |
| **把现有助手缩为“当前提案检查器”** | 回收现有工具和流式对话投资；可问来源、差异、历史类似案例 | IDE 的上下文宿主、call-center assist 的局部辅助 | 容易掩盖缺失的控制平面；同模型自解释不能替代独立证据；低使用率仍可能持续 |

这些候选之间真正的分歧不是“保不保留 AI”，而是优先修哪一层：**权威边界、产出入口、审查质量、模式感知，还是屏幕职责。**

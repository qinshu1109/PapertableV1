## 这件事是干什么的（大白话）

现在镇纸是一块**挂在墙上的仪表盘**（浏览器开 127.0.0.1:4317）：六个屏把押注、金子墓碑、候选卡、观众声音、数据回流、大盘账本摆给你看。但你想跟 AI **讨论**这些东西的时候，得自己把屏上的内容复述给 AI——数据在墙上，对话在别处，中间隔着一次"人肉搬运"。

这次要做的事：把 dsh（DeepSeek Harness 的聊天工作台）变成镇纸的**桌面**。六个屏的数据以侧栏面板、@引用、斜杠命令的形式长进 dsh——你在对话里 @某张押注卡，AI 立刻看到这注的赌约、产出、回流数据和相关判例，直接基于真数据帮你摆证据。墙上的大屏继续挂着（一个字不改），桌上多了个能对话的工作台。

参考样板是 B 站 UP 主 oil欧呦的「Oil Creator」：他把自媒体内容管理长进了 dsh（左栏内容列表、点开看各平台播放数据、对话里 @条目让 AI 改脚本）。**我们借他的壳（三栏交互、@引用、插件+技能打包），不借他的魂（他是内容发布管理，我们是决策判断协作）**——差异详见第五节。

## 怎么算好（总验收，按期细分见第四节）

- **P0 验收**：在 dsh 会话里 @一张真实押注卡问"这注离结账还有几天、数据够不够裁"，AI 引用真实数据文档答出来；同时镇纸大屏开着，两边数字一致。全程 AI **没有任何办法**替你结账——不是"它不敢"，是它的工具箱里根本没有这把工具（可查请求日志验证）。
- **P1 验收**：早上打开 dsh，先看到昨夜筛好的候选卡（推式，人从看开始不从问开始）；点「挑」生成押注草稿、人确认后转正；候选卡面上永远不出现"推荐"两个字。
- **P2 验收**：结账日到了 dsh（或微信）提醒你去裁决；对话聊某注时 AI 能带出相关旧笔记；dsh 里的镇纸面板是纸感浅色，不是深色数据板。
- **贯穿红线**：判断权永远在人（结账/确认类动作在 AI 工具面不存在）；Memos 只读；数据只有一份真身（papertable.sqlite3，一切经 4317 API 读写，dsh 不另存副本）。

## 一、六屏角色重定义：在 dsh 协作场景下各是什么

总原则一句话：**"判"的对象上面板（人要看着它聊），"看"的数据做工具（AI 要用时再查），"协作"的动作进会话（起草归 AI、裁决归人）。**

| 屏 | 类型 | 在 dsh 里的角色 | 具体交互 |
|---|---|---|---|
| **押注台** | 判 | **主角：@引用的对象 + 详情面板**。押注卡之于镇纸 = 内容条目之于 Oil Creator | 左栏「押注」列表（状态徽章：押注中/距结账 N 天/待裁决）；点开=单卡详情面板（三行赌注+置信度+产出物+最新数据文档）；会话里 `@押注卡` 注入装配上下文（assembleJudgmentContext 产出的只读 Markdown）；`/bets` 列在途 |
| **金子墓碑库** | 判 | **判例库：检索工具为主，面板为辅**。AI 答题时引判例（§N 编号已有），人复核时点开原文 | 工具 search_verdicts / read_verdict_evidence 直接搬；面板做一个轻量"判决簿"页（金印章/石碑条目，可检索）；`@金子` 把某条 lesson 注入上下文 |
| **协作台** | 协作 | **被 dsh 吸收的那个屏**。层2 对话职能整体迁入 dsh 会话；层1「今日值得看」变成 dsh 的落地面板 | dsh 打开镇纸区默认落「今日值得看」：筛子状态条+候选卡 grid（挑/改/否三按钮，**按钮是人点的**，点「挑」走既有 pick API 生成草稿）；对话就是 dsh 会话本身 |
| **观众声音** | 协作 | **skill + 摆盘面板**。筛子继续以 skill 形态后台跑（已趟通），dsh 面板只做筛后结果的三层密度摆盘 | 工具 read_voice / list_sieve_cards / read_corpus_comments 搬入；`@某视频评论区` 把 8 桶筛后摘要注入上下文；原文永远可展开（逐字原文，不替人下结论） |
| **运维 + 数据源** | 看 | **纯工具 + 通知，不做面板**。这是供血后台，AI 该替人盯着，而不是让人多一个屏要看 | 工具 read_connections（连接状态/风控事件）已有；needs_human（等人工接手）、到期未结账 → 注入 dsh 会话通知（P2 可走 dsh-wechat 到手机）；同步/抓取的运维明细留在镇纸运维屏 |
| **大盘 + 笔记** | 看（大盘）/ 协作（笔记） | **大盘留在墙上，笔记进会话**。大盘是周/月复盘仪式，校准曲线的价值在"定期面对"，不在"随时可查"；笔记的价值恰好相反——在聊某注时被"顺手带出来" | 大盘：dsh 侧最多一张只读数字卡（金/碑/押注中三数字），校准曲线**不搬**；笔记：回捞函数（recallPwNotesForBet，按押注捞相关旧笔记）做成工具，@押注时自动附带命中笔记；Memos 只读纪律原样带入 dsh 侧 |

两个刻意的"不对称"：

1. **押注台在镇纸是驾驶舱，在 dsh 是名片夹。** 镇纸押注台的回形针卡、闭环流程带、开干三槽是仪式感设计，不搬；dsh 里的押注卡是**为对话服务的引用物**——列表薄、详情面板只摆判断要素（赌约/数据/距结账天数）。想看仪式，回墙上看。
2. **协作台是唯一"被吃掉"的屏。** 其余五件在 dsh 里都是"分身"（数据同源、形态更轻），只有协作台是"搬家"——它的存在理由（推式大屏+对话）与 dsh 本体完全重叠。长期双轨维护两套对话 harness 没有意义，建议 P1 验证后冻结镇纸自建对话（详见开放问题 1）。

## 二、哪些上面板、哪些做工具/skill

判据三条：**人需要扫视的**（一眼看多条、比较、挑）上面板；**AI 需要引用的**（查单条、检索、算天数）做工具；**重活且离线的**（批量筛评论、生成类）做 skill。同一数据既要扫视又要引用的，面板和工具**调同一条 API**，不做两套逻辑。

**上面板（就 3 件，克制）**：
1. 押注列表 + 单卡详情面板（P0）——判的对象，人看着它聊
2. 今日值得看（P1）——推式起点，候选卡要横向比较着挑
3. 判决簿轻量页（P0 顺手，或 P1）——金子墓碑检索复核

**做工具（大头，且基本零新建——从 pw-collab-tools.ts 平移语义）**：

| dsh 工具 | 干什么 | 现成度 |
|---|---|---|
| read_bet / read_data_docs / read_doc_versions | 查押注全文、回流数据文档、版本链 | ✅ 已有 |
| search_verdicts / read_verdict_evidence | 检索金子墓碑、看判决证据链 | ✅ 已有 |
| read_voice / list_sieve_cards / read_sieve_card | 观众声音、筛子候选卡 | ✅ 已有 |
| list_corpus / read_corpus_doc / read_corpus_comments / search_corpus | 语料库四件套 | ✅ 已有 |
| read_connections | 数据源连接与风控状态 | ✅ 已有 |
| recall_notes_for_bet | 按押注回捞相关旧笔记（Memos 只读） | 后端函数已有（PW-40），包一层工具即可 |
| draft_bet（P1 起）| AI 起草押注，人确认转正 | ✅ 已有，走 dsh-proposal-gate 同款通道隔离 |
| **settle / confirm 类** | —— | **永不存在。不是 deny，是没有。** |

**做 skill**：评论筛子（voice-comment-sieve，已在跑）、结账前证据打包（把某注的全部数据文档+相关判例整理成裁决材料——AI 摆证据的集大成动作，产出仍是"材料"不是"建议"）、封面/标题起草类（对应 Oil 的生成技能，产出全部落草稿）。

**明确不上 dsh 的**：校准曲线与目标进度（大盘独占）、闭环流程带（押注台仪式）、运维同步明细（工具可查就不占屏）、看板/日历/甘特（否定验收永久继承）。

## 三、镇纸大屏（4317）与 dsh 面板的分工 + 单一事实源

**分工一句话：墙上的仪表 vs 桌上的工作台。** 大屏管"状态呈现与仪式"（推式、全景、定期面对），dsh 管"协作动线"（引用、追问、起草、确认）。六屏在 4317 上**零改动**——这不是过渡期妥协，是长期分工：同一份数据，墙上看势，桌上办事。

单一事实源三条军规（给任务 A / 实现期的基调建议）：

1. **只有一份真身，只有一个门。** 数据真身是 papertable.sqlite3 + data/corpus/ 文件；dsh 插件（node 半插件）**只走 127.0.0.1:4317 HTTP API，不直连 SQLite 文件**。理由不是连不上（同机 WAL 并发读可行），而是 API 层收口了业务规则——"数据文档只增不改""draft 对正式区不可见""镜像单向"这些纪律都在 API/函数层，绕过它等于开第二套规则解释权。dsh 面板每次现拉（个人量级毫秒级响应），**不建本地缓存/镜像表**。
2. **写路径漏斗形。** dsh 侧能落库的写只有三类：起草类（draft_bet 等既有 API，产草稿）、人点按钮直连 API（挑/改/否、面板上的人工操作——这是"人在 dsh 界面操作镇纸"，不是"AI 写"）、skill 判决导入（对账不过不落库，PW-65 纪律照旧）。结账/确认永远只发生在：镇纸屏，或 dsh 面板上**人点的**确认按钮（直连 API，decided_by=human 数据库约束兜底）。
3. **账本各记各的，靠 hash 勾稽。** 镇纸的 pw_runs 审计账继续在 API/函数层单点记（现状如此，dsh 接入不需改）；dsh 的会话日志归 dsh。AI 草稿被人确认时，确认记录引用 draft_hash（既有机制）——两边日志靠这个 hash + 时间戳对得上账，不搞双写日志同步。

## 四、分期方案

分期不写日期写闸门（继承 PRD 纪律：闸门不过不开下一期）。

### P0 · 把"判的对象"放进对话 —— 押注台 + 金子墓碑库

选这两个屏开局（与简报建议一致，且证据支持）：数据已持久化最完整（18 注 3 判决 3 金镜）、协作价值最高（判决上下文注入是镇纸独有能力）、**且几乎纯只读**——风险最小的一期恰好是价值最大的一期。

范围（四件事）：
1. dsh 左栏「押注」tab：在途押注列表（标题+状态徽章+距结账天数），点开单卡详情面板（三行赌注/置信度/产出物/最新数据文档摘要/相关判例 §N）
2. `@押注卡` 引用：把该卡装配上下文（只读 Markdown）注入会话；`/bets` 斜杠命令列在途
3. 只读工具五件套接入：read_bet / read_data_docs / search_verdicts / read_verdict_evidence / read_doc_versions
4. 判决簿轻量页（金/碑列表+检索）——若插件工作量紧张可降级为纯工具，P1 补页

**P0 闸门（现象级验收）**：
- 在 dsh 会话 @真实押注卡，问"这注离结账几天、回流数据够不够裁"，AI 引用真实数据文档与相关判例（§N 可点开复核）答出，全程未手工投喂数据
- 请求日志里 AI 的工具数组**不含任何 settle/confirm 类 schema**（dsh-proposal-gate 同款验证法）
- 大屏与 dsh 面板同时开，押注数、判决数、最新数据文档三处数字一致
- 面板为纸感浅色（--pw-paper 系 token），非深色数据板
- 否定验收：无看板/日历/甘特；卡面无"推荐"字样

### P1 · 把"推式"搬进来 —— 今日值得看 + 观众声音 + 起草通道

前提：P0 闸门过，且用户实际用 dsh 聊过至少一圈真实押注（不是演示数据）。

范围：
1. dsh 镇纸区落地页 =「今日值得看」：筛子状态条（昨夜已筛 N 批/有新数据待筛+补筛按钮）+ 候选卡 grid（四字段+挑/改/否，人点）
2. 筛子调度迁到 dsh-scheduled-prompt（定时+预算护栏现成），产出照旧不写正式表
3. 观众声音筛后摆盘面板（8 桶+逐字原文展开）+ 语料四件套工具
4. 开放 draft_bet 起草通道：AI 在会话里起草押注 → 提案通道（dsh-proposal-gate 模式）→ 人在面板确认转正（记 draft_hash）
5. `/current-bet`（仿 Oil 的 /current-content）：把当前打开的押注卡注入上下文

**P1 闸门**：
- 连续 7 天，早上打开 dsh 首屏是昨夜筛好的候选卡（推式成立）
- 完整走一次"AI 起草 → 人改 → 确认转正"，pw_runs 里 ai_draft 与 manual 账目分明、draft_hash 勾稽成立
- 镇纸自建协作台层2在这 7 天内自然零使用 → 触发开放问题 1 的拍板（冻结或保留）

### P2 · 收口 —— 通知、笔记、品牌

范围：
1. 提醒注入:到期待裁决、needs_human、镜像同步失败 → dsh 会话通知，可选 dsh-wechat 推到微信
2. recall_notes_for_bet 工具：@押注时自动附带相关旧笔记（命中词+回链，Memos 只读）
3. 大盘只读数字卡（金/碑/押注中三数字，不搬曲线）
4. pw-theme 品牌插件：纸感 token 移植（Oil 证明了品牌定制走插件可行）

**P2 闸门**：
- 一次真实结账由 dsh 提醒触发、人在镇纸（或面板人按钮）完成裁决，全程 AI 未碰裁决
- 聊任一在途押注，相关旧笔记自动到场且回链可跳 Memos
- dsh 内镇纸面板与 4317 大屏视觉同源（token 一致）

### 永不做

AI 可调用的结账/确认工具；dsh 侧第二份数据副本；深色数据板皮肤；看板/日历/甘特；卡面"推荐"字样。

## 五、与 Oil Creator 的差异（不能照抄的地方）

他做的是**内容发布管理**（作品是主角，闭环止于"看数据"），镇纸做的是**决策判断协作**（判断是主角，数据是证据，闭环必须走到"裁决"）。八条差异：

| # | 维度 | Oil Creator | 镇纸 × dsh |
|---|---|---|---|
| 1 | 核心对象 | 内容条目（视频/脚本/字幕——产物） | 押注卡（假设/指标/结账日——判断） |
| 2 | 闭环终点 | 发布后看播放赞评，**止于看** | 数据回流后**必须裁决**（金/碑/作废），进校准 |
| 3 | AI 的手脚 | 执行型副驾：agent 直接新建条目、改脚本、生成封面（重活在工具里，AI 有写权） | 证据型副驾：AI 摆证据不给结论；写路径只有草稿；裁决工具 schema 不存在。**Oil 的 agent 是手，镇纸的 agent 是眼** |
| 4 | 状态语义 | 待发布/已发布——工作流状态，可自动流转 | 押注中/金子/墓碑/作废——判决状态，**只有人能迁移**（DB 层约束） |
| 5 | 数据角色 | 平台数据 = 成绩展示（概览页数字卡） | 数据文档 = 结账证据（只增不改、冻结、被判决引用） |
| 6 | 面板/工具重心 | 重面板（内容管理是主场景，五 tab 详情） | 重工具+上下文注入（判断协作是主场景，面板只是摆证据的桌面） |
| 7 | 排序与推荐 | 无此顾虑 | 停线纪律：排序 √（依据印在卡上可复核）推荐 ×（卡面永不出现"推荐"） |
| 8 | 视觉 | 深色科技风 | 纸感浅色（硬约束，token 现成） |

**可以放心照抄的**：三栏信息架构（左列表/中详情/右会话）、@引用与斜杠命令交互、"模型只负责执行、重活在工具里"（DeepSeek-V4-Flash 级模型即可跑，因为镇纸的重活——筛选、检索、装配——全在工具层）、"dsh 插件 + skills"打包形态、品牌定制走插件。

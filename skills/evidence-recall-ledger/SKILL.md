# evidence-recall-ledger：证据召回漏斗账本与显式引用审计

系统会把知识条目（旧笔记、历史决策、检索结果、记忆片段）摆到人或模型面前，但「摆过 ≠ 用过」。在改进任何召回/推荐功能之前先把账记清楚——否则分不清使用率低是「没召回」（根本没摆出来）还是「召回了没人用」（摆了但断在采纳环节），改功能就是盲改。两个模式都是纪律文本，零代码即可先跑起来。

## 模式一：召回漏斗账本

### 六种事件

| 事件 | 含义 | 谁能写 |
|---|---|---|
| surfaced | 系统把某条目摆到人面前 | **仅 AI/系统** |
| confirmed | 人确认该条目相关 | 仅人触发的动作 |
| rejected | 人拒绝该条目 | 仅人触发的动作 |
| attached | 人把条目挂接到某个工作对象 | 仅人触发的动作 |
| used | 人确认实际用上了 | 仅人触发的动作 |
| settled | 收尾/复盘时归因到该条目 | 仅人触发的动作 |

### 红线

**AI/系统只许写 surfaced；confirmed/rejected/attached/used/settled 五种只能由人触发的既有动作产生。** 打点只挂在现有的人工入口上，不为记账发明新的「人确认」流程。AI 替人补写采纳事件＝账本作废——这本账度量的正是人的真实采纳行为。

### 记账维度：按「出口」记

每行事件带上它发生的**出口通道**（surface：条目从哪个界面/管道摆出来）。统计按 出口 × 事件档 交叉，才看得出「哪个出口摆得多但没人认」「哪个出口摆一条中一条」。最小账本行：

```text
{事件 id, 时间, event_kind（六选一）, surface（出口通道）, 条目 id, 关联工作对象 id?, 补充信息?}
```

### 立意与预留

- **先拿分母再改功能**：surfaced 是分母，confirmed/attached/used 是分子；没有这本账，任何「召回效果」的讨论都是无分母的感觉。
- **某档没有入口就不产生**：如 used 暂无人工确认入口，则该档恒为空——保留枚举、不造流程，等真实入口出现再打点。空档本身就是信息（说明产品还没有「确认用上」这个动作）。
- **打点是旁路**：写事件失败不得影响宿主流程（该摆出的照常摆出），失败静默记警告即可。

## 模式二：提供↔引用↔审计契约

用于「系统把知识条目直接提供给模型」的场景，回答「模型到底引用了哪条」：

1. **全量提供，封顶 N 条**：每个干净上下文（新会话/新任务）一次性提供全部有效知识条目，数量上限 N（示例 N＝10；超上限说明知识集该收敛，而不是该分页）。每条带稳定 id。
2. **显式引用标注**：约定模型凡采用某条目，必须在回答中显式写 `[[id]]`；不标注＝视为未引用。
3. **系统解析落审计**：系统解析模型回答，落一条审计记录：`{provided: [提供的 id 列表], used: [解析出的 id 列表], unknownCount: 解析出但不在提供列表里的标注数}`。

### 为什么是「模型自标」而不是「系统猜」

该契约是一次真实证伪后的改版：最初版本由系统侧对模型回答做字符串匹配来猜「哪条被用了」，真实数据下**命中 0**——模型采用知识时会改写、融合、意译，字符串匹配根本对不上。教训：**让模型自己选择并显式标注，胜过系统侧的猜测匹配**；可审计性要设计进输出约定里，而不是事后考据。

## 两个模式怎么选

- 条目摆给**人**看、人来采纳 → 模式一（度量人的采纳漏斗）。
- 条目提供给**模型**、模型来引用 → 模式二（度量模型的引用行为）。
- 两者可并存、各记各的账，不互相替代；共守一条底线：**采纳/引用的判定不由提供方自说自话**——模式一交给人的动作，模式二交给可解析的显式标注。

## 落地检查清单

- [ ] 事件枚举与出口通道清单写死；无入口的档明确「不产生」
- [ ] AI/系统侧只可能写 surfaced（其余档只在人工入口处打点）
- [ ] 打点失败不影响宿主流程
- [ ] 有按 出口 × 事件档 的统计口径（哪怕先手算）
- [ ] （模式二）N 值已定；`[[id]]` 约定写进给模型的说明；审计记录含 provided/used/unknownCount

## 出处

两个模式源自 Papertable：模式一为镇纸笔记召回事件账本（pw_recall_events，六档 × 四出口，红线「AI 只许写 surfaced」，简报 12）；模式二为判决复用契约 TASK-KU-001 v2（v1 的系统侧字符串匹配被真实数据证伪、命中 0 后的改版）。

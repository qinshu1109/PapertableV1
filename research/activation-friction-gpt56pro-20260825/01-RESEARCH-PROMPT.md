# 研究题干：工作台激活阻力 × DeepSeek Harness 插件侧车

请按本文做一次跨领域研究。`sources/` 里的文档只在你需要核对结构名称或既定边界时打开。不要把那些 TASK/SPEC 当成开发任务。不要输出实现步骤、代码或产品路线图。

---

我在维护一个本地个人知识与内容决策系统，遇到的不是“功能不够”，而是
“系统已经做成了，我却因为琐事太多一直没用”。在笔记软件 / PKM / 个人
工作台这个领域里，常见补丁全是：再加一个首页、再加一个日报、再加一个
待办队列——都假设人会主动打开那个界面。我怀疑这个假设是错的。所以我
来找别的领域有没有早就解决过同构问题的——请把这当一次跨领域研究来做。
DeepSeek Harness 的社区插件最近很火（有的安装量已经 1 万+），我想重点
看这类“插件侧车”以及其它领域里真正把人从‘走进控制室’改成‘信号找
到人’的机制；安装量本身不是证据，不要把它当成功证明。

【我的坑，如实描述】
系统两张脸已经能跑：纸桌用来想，镇纸用来定。笔记可以从手机飞书写进库，
镇纸能读、能捞、能卷积、能在 DeepSeek Harness 会话开头塞一段快照。但
我日常被琐事占满，不会专门打开 http://127.0.0.1:4317 的探索/镇纸界面。
我直觉：主动打开的阻力太大；应该改成“每天有东西弹到我手机上”，人只
在被打断、且打断值得时才进入可视化层。

2026-08-25 本机只读快照（http://127.0.0.1:4317，不是印象；明细见 02-LIVE-SNAPSHOT.md）：
- Memos 笔记可被镇纸读取：近 7 天口径 541 条，窗口内新增 11 条。
- 内容押注 0、普通押注 0；收工小结写明「当前无在途内容押注，今日不捞」。
- 筛子待选 0、语料 0、观众声音 0、弹药架空。
- 纸桌探索项目 39 个；镜像金子 3 条（来自纸桌已确认判断，不是镇纸结账产出）。
- B 站连接 1 条（「琴疏的B站」，active，从未同步）。
- 当日协作台事件 0。

也就是说：捕捉端（飞书→笔记）还在进料，决策端是空台，人也没进去用。
空台 + 不打开，是同一天同时成立的两件事，请不要只解释其中一件。

我的候选补丁（未拍板，请当“待验假设”而不是方案）：
用 DeepSeek Harness 插件，每天读取我经飞书记到 Memos 的笔记，把处理结果
推到手机，而且要能弹起手机通知；人被通知拉动之后，再在镇纸 Paperweight
里可视化、继续推动；遇到模糊、或 AI 误区比较大的问题/方向，才打开纸桌
Papertable 去梳理。

我怀疑这个补丁可能只是换了一个“会响的首页”。我已经有三条几乎同构、
但没让我养成打开习惯的通路，请把它们当已试过的补丁，不要假装从零发明：
1. 镇纸后端每天 06:30 捞料（无在途押注则跳过）+ 笔记自动卷积（30 分钟巡检，
   日/周/月报草稿）。产出都躺在镇纸笔记屏上，等人打开。
2. dsh-paperweight 插件：会话开始 4 秒内拉快照，塞一条 ≤900 字 notice；
   另有本地推送收件箱。插件铁律写明「通知不绕微信；推送走 dsh 面板」——
   人不打开 dsh web / 镇纸，就收不到。
3. dsh-wechat：微信里对话、审批、摘要推送（非官方 iLink 网关）。2026-08-15
   已拍板：微信通道保留其推送触达价值，dsh web 无推送能力，两者定位不同。
飞书通道被核实过：只有速记中继，不是 agent，没有 /new、skills、审批、
定时 agent 联动。

【系统背景，供你定位结构】
两个产品、同一仓库、同一进程、同一 SQLite。名称不许搞混：
- 纸桌 Papertable（思考场）：「意图 → 想法 → 选题」的探索与求证。项目、
  卡片、深挖/发散/改道、把已确认判断标成金子/墓碑。“把纸摊开让你想。”
- 镇纸 Paperweight（判断闭环 / 内容生产工作台）：「押注 → 开干 → 数据回流
  → 结账」。选题候选、素材草案、在途押注、笔记大盘、收工小结都在这里。
  “把纸压住让你定。” 既定方向（2026-08-04 拍板，不用重议）：镇纸是内容
  生产工作台，不是事后复盘的马后炮项目。
- 金子同步单向：纸桌确认的金子流入镇纸；镇纸写路径不触达纸桌判决表。
- 笔记真值在 Memos（本机 127.0.0.1:5230）。镇纸只读，不复制、不碰 Memos
  的 SQLite。飞书速记中继（独立进程，不进镇纸库）= 手机飞书 P2P 文本 →
  去重 → 写 Memos 官方 API → 回执「已记」。所以“飞书记载到 memos 的笔记”
  已经在 Memos 里，镇纸与任何插件读笔记应走 Memos/4317，不是再去爬飞书。
- DeepSeek Harness（dsh）是本机 agent 运行时，不是纸桌/镇纸本体。web 在
  127.0.0.1:3080，launchd 常驻；手机外网访问走本机隧道，明确不部署到
  4G 内存的生产机（既定，不用重议）。插件是 Cordis bundle。我已有：
  dsh-scheduled-prompt（cron 或固定秒周期；target=self 时 idle 用 followup、
  busy 用 inject，错过的 tick 不补跑；new-session 每次起一次性 agent；
  预算护栏 + JSONL 审计）；dsh-paperweight（数据只打 4317 HTTP，不直连库、
  不建镜像表；AI 工具面 8 只读 + 起草草稿；人点按钮才转发写动作）；
  dsh-wechat（微信 ⇄ agent）。社区插件生态是我这次想重点对照的实践来源，
  但“1 万+ 安装”只说明分发面，不说明它解决了我的激活问题。

铁律（既定，不用重议）：
- AI 摆证据、降筛选成本，不做决定；人发话才写正式状态。
- 原文原则 / 异类保留 / 判断留人。
- 不做看板、日历、甘特。
- 对话即控制台：人可以不点按钮，但不能把“人没发话”变成 AI 替人拍板。

资产流向（与本题有关的一段）：
手机飞书速记 → Memos 真值库 →（镇纸只读）笔记屏 / 卷积 / 捞料候选
→ 人确认才挂到在途押注 → 草案 → 成品 → 回流 → 结账。
当前断在两处：①没有在途押注，捞料按规定空跑；②即使有产出，也要我主动
打开镇纸或 dsh 面板才看得到。候选补丁试图在 ② 上加手机弹窗，并把模糊
问题分流到纸桌。

不要再研究「库存条目判完沉底怎么被用」（2026-08-12 已单独投过一轮，
馆藏流通/卢曼卡片盒/呆滞料那套）。本题是：控制室建成了，人为什么不进去，
以及“让信号来找人”会不会只是另一种无人值守的警报。

【我要你研究的问题】
1. 同构检索：人类历史上哪些领域面对过“控制室/仪表盘已经建好，操作者
   却因为琐事与激活能量进不去，必须改成信号找人”，并且真的把使用发生
   了？候选请你验证真伪同构并补充：
   - DeepSeek Harness / OpenClaw / Hermes 这类 agent 插件与即时通讯侧车
     （cron followup/inject、摘要推送、审批进聊天，而不是再做一个 Web 控制台）
   - 航空 TCAS / 医院 ICU 警报 / SRE on-call 与警报疲劳
   - 交易员：彭博终端 vs 手机紧急单
   - 军事 Commander’s Critical Information Requirements（什么才配打断指挥官）
   - 丰田 Andon（异常拉绳找人，而不是人去盯看板）
   - 情报界 PDB（总统每日简报）vs 自己打开仪表盘
   - GTD tickler / Things 晚间回顾 / 宗教定时召唤（钟声、唤礼）
   - BJ Fogg 微习惯与激活能量；邮件打败 RSS（推送到已打开的盒子）
   - Raycast / Alfred / VS Code 插件当侧车，而不是再开一个目的地 App
   - iOS 通知中断级别（Time Sensitive vs 普通横幅）与用药提醒 App 的高弃用
   - 微信工作通知 vs 飞书/企微“还要打开工作台”
   请点名哪些只是表面像（都有通知），哪些机制真的改变了“人会不会出手”。

2. 机制提炼：被验证的机制里，“让人在琐事流里仍然完成判断动作”是怎么
   运转的？请拆开这些件，不要揉成一句“要推送”：
   - 打断权：谁有权响、一天允许响几次、什么级别必须弹起、什么只进收件箱
   - 载荷：响的那一下带的是可裁决的最小证据，还是又一份摘要要人去打开大屏
   - 闭环地点：判断是在通知里做完，还是通知只负责把人拖回控制室
   - 空台策略：当下游对象（我这里是在途押注）为零时，系统是沉默、催生对象，
     还是改推别的东西
   - 侧车 vs 目的地：插件/聊天/通知作为主入口时，原控制室如何避免变成遗迹
   各机制的前提与失败模式是什么？尤其是警报疲劳、把推送做成又一个未读堆。

3. 补丁定位：我的候选（dsh 插件每日读 Memos 笔记 → 手机弹窗 → 镇纸可视化
   再推 → 模糊问题去纸桌）放在这些机制里属于哪一类？请逐条检验它的致命
   假设，至少覆盖：
   - 假设 A：不打开是因为入口不对，不是因为没有可判的对象（当前押注=0）
   - 假设 B：需要再去“读飞书”；实际上笔记已在 Memos，飞书只是写入端
   - 假设 C：弹起手机通知 = 判断会发生；会不会只是换了一个未读徽章
   - 假设 D：dsh 插件是新通道；它与已有 notice / 面板收件箱 / 微信摘要 /
     镇纸笔记屏是什么关系，会不会四路抢同一注意力
   - 假设 E：模糊问题分流到纸桌，仍要求我主动打开纸桌——激活阻力是否只是
     换了一张脸
   - 假设 F：社区插件 1 万+ 安装说明这个形态适合我这种单人决策闭环
   有没有第三条我从“加推送”里看不到的路？只摆机制，不替我选。

4. 度量：我现在能数的是打开次数≈0、押注=0、笔记仍在进（541 / 7 天 +11）、
   捞料因无押注按规定不跑。上述领域用什么指标区分“推送成功”和“判断发生”？
   我的指标有没有结构性盲区——比如把“响了”当成“用了”，或把“空台不响”
   误判成健康沉默？有没有领域认为“建成但很少打开”在这个阶段其实正常？

5. AI 分工边界：铁律是 AI 摆证据、人下判断。每天读笔记并推到手机，哪些
   是合规的“摆”（例如：今天新增 11 条里逐字摘出与在途押注对得上的原句；
   没有在途押注就只报“空台+新笔记条数”），哪些是越权的“判”（例如：
   今天该押哪题、这条笔记重不重要、该不该打开纸桌）？手机弹窗的字数和
   动作（已阅 / 挂押注 / 打开镇纸 / 打开纸桌）怎样才不把决定权偷走？

6. 与纸桌 / 镇纸 / dsh 结构的咬合：
   - 推送载荷的数据应从哪读：Memos、镇纸 4317、dsh 插件本地收件箱？
   - 弹窗通道已有一次拍板（微信管触达，dsh web 管完整体验，dsh-paperweight
     写明不绕微信）。候选要“手机弹起通知”，是在沿用这次拍板、修改它，
     还是开第三通道（飞书机器人回执目前只有「已记」）？
   - 镇纸作为可视化决策层、纸桌作为模糊问题梳理层，这个分流在其它领域
     有没有同构（例：例外进战情室、日常在耳机里裁决）？哪种咬合最不容易
     变成“两个都要打开、于是两个都不打开”？
   - dsh-scheduled-prompt 的 self/inject、错过不补跑、预算护栏，和
     “每天一次、必须弹起”之间有没有机制冲突？
